## 1. 现有单机 VLFM：数据流

配置入口是 `config/experiments/vlfm_objectnav_hm3d.yaml`，策略是 `HabitatITMPolicyV2`，只有 1 个环境。

### 1.1 每一步发生了什么

评估循环在 `vlfm/utils/vlfm_trainer.py`（`_eval_checkpoint`）。每一步：

1. **环境给出观测**（`self.envs.step` → `batch_obs`）。用到的键：`rgb`（480×640）、`depth`（归一化到 [0,1]，对应 0.5–5.0 m）、`gps`、`compass`、`heading`、`objectgoal`。
2. **`HabitatMixin.act`**（`habitat_policies.py:121`）把目标类别 id 换成名字（HM3D 六类：chair、bed、potted plant、toilet、tv、couch），再调用父类。
3. **`ITMPolicyV2.act`**（`itm_policy.py:251`）依次做三件事：
   - `_pre_step`：如果是新 episode（`masks == 0`）就重置所有地图；然后调用 `_cache_observations`。
   - `_update_value_map`：更新价值地图。
   - `BaseObjectNavPolicy.act`：更新物体地图，决定模式，输出动作。

### 1.2 观测 → 障碍物地图 → frontier

在 `HabitatMixin._cache_observations`（`habitat_policies.py:173`）里：

1. 深度图先过 `filter_depth` 去噪。
2. 由 `gps` 和 `compass` 算出相机位姿矩阵 `tf_camera_to_episodic`（见第 2 节）。
3. `ObstacleMap.update_map`（`obstacle_map.py:55`）：
   - 深度图反投影成点云，变换到 episodic 坐标系。
   - 只保留高度在 `[min_obstacle_height, max_obstacle_height]` = `[0.61, 0.88]` m 之间的点，画进障碍物栅格 `_map`。
   - 障碍物按机器人半径（0.18 m）膨胀，取反得到可通行栅格 `_navigable_map`。
   - 用 `reveal_fog_of_war` 从机器人位置按视场角（79°）和最大深度（5 m）打射线，得到这一步新看到的区域，并入 `explored_area`。
   - **如果已探索区域有多个不连通的块，只保留包含机器人的那一块**（`obstacle_map.py:133–146`）。这一点对双机器人很重要，见 3.3。
   - `detect_frontier_waypoints` 在"已探索"和"可通行但未探索"的交界上找 frontier；交界外的未探索面积小于 1.5 m² 的会被丢掉。结果是一组 (x, y) 路点，存在 `ObstacleMap.frontiers`。

注意：frontier 是 VLFM 自己用深度图算出来的，不是 Habitat 的 `frontier_sensor` 给的。后者用了真值导航网格，这里只用于可视化。

### 1.3 观测 → 价值地图

`BaseITMPolicy._update_value_map`（`itm_policy.py:191`）：

1. 把当前 RGB 和提示语 `"Seems like there is a <目标> ahead."` 送给 BLIP-2 ITM server，得到一个余弦相似度（标量，实际多在 0.1–0.25）。
2. `ValueMap.update_map`（`value_map.py:100`）：
   - 生成一个扇形的置信度掩码：视场中心置信度为 1，向两侧按 cos² 衰减到 0.25。
   - 用深度图把扇形裁到实际可见的范围（被墙挡住的部分去掉）。
   - 按机器人朝向旋转，贴到地图上机器人所在的像素位置。
   - 融合（`_fuse_new_data`）：配置里 `use_max_confidence: false`，所以每个像素是**按置信度加权的平均**：`v = (c_old·v_old + c_new·v_new) / (c_old + c_new)`，置信度本身也做加权更新。新置信度低于 0.35 且低于已有置信度的像素会被忽略。

价值地图存两层：`_map` 是置信度，`_value_map` 是价值。融合规则只依赖"这个像素被谁、以多大置信度看到"，和是哪个机器人看的无关。这使得两台机器人共用一张价值地图在数学上是直接成立的。

### 1.4 观测 → 物体地图

`BaseObjectNavPolicy._update_object_map`（`base_objectnav_policy.py:281`）：

1. 目标属于 COCO 类别时用 YOLOv7（阈值 0.8），否则用 GroundingDINO（阈值 0.4）。HM3D 的六类都走 YOLOv7。
2. 每个检测框送给 Mobile SAM 得到掩码，把掩码内的深度反投影成点云，变换到 episodic 坐标系，存进 `ObjectPointCloudMap`。
3. `update_explored`：如果某团点云当初是在"超出可靠深度范围"时记录的，现在它落在相机视锥内却没被再次检测到，就把它删掉。

### 1.5 模式切换和 frontier 选择

`BaseObjectNavPolicy.act`（`base_objectnav_policy.py:106`）按顺序判断：

- **initialize**：前 12 步原地左转（每步 30°），看一圈。
- **navigate**：物体地图里已经有目标 → 用 PointNav 走向目标点云上离自己最近的点，距离小于 0.9 m 时调用 STOP。
- **explore**：否则，选一个 frontier 走过去。

frontier 选择在 `BaseITMPolicy._get_best_frontier`（`itm_policy.py:76`）：

1. `ValueMap.sort_waypoints(frontiers, 0.5)`：每个 frontier 的分数是它周围 0.5 m 半径内价值的最大值，按分数从高到低排序。
2. **粘滞**：如果上一步追的 frontier 还在（或 0.5 m 内有一个），并且它现在的分数 + 0.01 仍高于上次的分数，就继续追它。
3. 否则取分数最高、且不构成循环的 frontier（`AcyclicEnforcer` 记录"位置—frontier—前两名分数"的组合，本意是避免来回摆）。

**上游 bug**：`AcyclicEnforcer` 实际上从未生效。它的 `StateAction` 只定义了 `__hash__`，没有定义 `__eq__`，集合查找按对象身份比较，所以 `check_cyclic` 恒为 False。也就是说，已发表的 VLFM 的行为等同于没有这一步。处理方式：默认保持原样（与发表的 VLFM 一致），加配置开关 `fix_acyclic_enforcer`（默认 `false`）；所有方法使用同一设置。

选中的 frontier 交给 `_pointnav`：算出目标相对机器人的 (ρ, θ)，连同缩放到 224×224 的深度图送进预训练的 PointNav 策略（`data/pointnav_weights.pth`，带 LSTM 隐状态），输出离散动作：STOP、前进 0.25 m、左转 30°、右转 30°。

### 1.6 episode 结束和指标

Habitat 的 ObjectNav 任务：最多 500 步；调用 STOP 时，机器人到目标任一可视点的测地距离小于 0.1 m 算成功；SPL = S·L / max(P, L)，L 是起点到目标的最短测地距离，P 是实际走过的路径长度。

## 2. 坐标系

一共四个，这里逐个说清楚，因为共享地图的前提就是把它们对齐。

| 坐标系 | 原点 | 轴 | 在哪里用 |
|---|---|---|---|
| Habitat 世界系 | 场景固定 | +y 朝上；机器人默认朝向是 −z | 仿真器内部、episode 的 `start_position`、导航网格 |
| Habitat episodic GPS | episode 起点 | `gps[0]` = 向前，`gps[1]` = **向右**；`compass` = 相对起始朝向逆时针转过的角度 | `gps`、`compass` 观测 |
| VLFM episodic 系 | episode 起点（地面） | x 向前，y **向左**，z 向上 | 所有地图、点云、frontier、PointNav 目标 |
| 地图像素 | 1000×1000，20 像素/米（50 m × 50 m），起点在 (500, 500) | 行 = 500 + 20·x，列 = 500 − 20·y | `ObstacleMap`、`ValueMap` 的数组下标 |

转换关系：

- **世界系 → GPS**（`habitat/tasks/nav/nav.py`，`EpisodicGPSSensor`）：`p' = R_start⁻¹ · (p − p_start)`，然后 `gps = [−p'_z, p'_x]`。
- **GPS → VLFM**（`habitat_policies.py:187`）：`camera_position = [gps[0], −gps[1], camera_height]`，把"向右为正"翻成"向左为正"。`camera_height` 是固定值 0.88 m。
- **相机位姿**：`tf_camera_to_episodic = xyz_yaw_to_tf_matrix(camera_position, compass)`，只有绕 z 的旋转加平移。
- **相机点云**（`geometry_utils.get_point_cloud`）：相机系本身就按 x 向前、y 向左、z 向上组织，所以乘上面的矩阵就到了 VLFM episodic 系。
- **VLFM → 像素**（`BaseMap._xy_to_px`）：见上表。可视化时上下翻转，所以图上"上"是起始朝向。

两点需要注意：

1. **z 是假的**。VLFM 假设地面是平的：相机高度永远是 0.88 m，不管机器人实际的世界 y 是多少。障碍物的高度筛选 `[0.61, 0.88]` 是相对这个假想地面的。同一楼层内地面有起伏时（场景 00853 里起点高度在 0.02–0.28 m 之间），会有少量误差，单机版就是这样。
2. **两张地图的取整方式不同**。`ObstacleMap` 用四舍五入，`ValueMap` 用截断，最多差 1 个像素（5 cm）。不影响使用，但做一致性测试时要留 1 像素的容差。

## 3. 双机器人方案

### 3.1 设定

- 两台机器人 R1、R2 找同一个目标。集中式、完美通信：一个协调器能看到两台机器人的全部观测和位姿。
- R1 用 episode 原本的起点。R2 的起始位姿离线生成一次，存成文件，所有方法共用。采样规则见 3.9。
- 任意一台在目标成功距离内调用 STOP，即为成功，episode 结束。
- 步数预算按**联合步**算：一个联合步里 R1、R2 各执行一个动作。主实验预算是 500 联合步。方式 C 下一个联合步等于两个环境步，所以环境的 `max_episode_steps` 设为 2 × 预算 = 1000。单机基线是 500 步。

### 3.2 统一坐标系

**共享坐标系 W 定义为 R1 的 VLFM episodic 系**，也就是原点在 R1 起点、x 沿 R1 起始朝向。它和 Habitat 世界系只差一个固定的刚体变换，所以是一个合格的"世界坐标系"。

选它而不是直接用 Habitat 世界系，原因有三个：

- Habitat 的 `gps`、`compass` 本来就是相对 `episode.start_position / start_rotation` 算的。只要 R2 的位姿也用同一个 episode 起点去算，R2 的观测**天然就在 W 里**，不需要额外的变换代码。
- 地图以 R1 起点为中心、50 m × 50 m 的布局不用改。直接用世界系的话，场景坐标可能偏离原点很远，要另外处理地图原点。
- 机器人数设为 1 时，行为和现有单机版完全一致，可以做逐 episode 的回归测试。

文档和代码里会提供 `world ↔ W` 的转换函数，用于 R2 起点的换算和测试。

关于"z 是假的"这一点：两台机器人共享地图时，如果 R2 起点的地面高度和 R1 差得多，障碍物高度筛选会错位。处理办法是采样 R2 起点时限制高度差（建议 |Δy| ≤ 0.2 m，同时这也是"同一楼层"的判据），其余保持单机版的平地假设，保证可比。

### 3.3 共享地图

三张地图都共享：障碍物地图、价值地图、物体地图。每台机器人每一步用自己的 (RGB, 深度, 位姿) 更新同一组对象。

需要改动的地方：

- **`ObstacleMap` 的"只保留机器人所在连通块"逻辑**（`obstacle_map.py:133–146`）。两台机器人在不同房间时，已探索区域本来就是两块；现有代码会把队友那块删掉。要改成"保留包含任意一台机器人的所有连通块"。
- **轨迹记录**。`BaseMap._camera_positions` 只有一条轨迹，要改成每台机器人一条，可视化时用不同颜色。
- **`AcyclicEnforcer.history` 原本是类属性**，所有实例共用同一个集合，而且跨 episode 不会清空。阶段 0 已改成实例属性。由于 1.5 里说的 bug，这个改动不影响行为，只是去掉了内存增长；打开 `fix_acyclic_enforcer` 之后，每台机器人必须有自己的实例。
- **价值地图**：融合规则与观测者无关（见 1.3），不需要改算法，只需要改轨迹显示。
- **物体地图**：点云已经在 W 里，`get_best_object(target, position)` 按传入的位置取最近点，天然支持多机器人。

每台机器人各自保留的状态：PointNav 的 LSTM 隐状态和上一个目标点、初始化转圈的计数、当前模式、上一次分配到的 frontier。

### 3.4 frontier 联合分配

协调器在每次有机器人需要探索目标时运行。输入：共享障碍物地图给出的 frontier 集合 F、共享价值地图、两台机器人的位姿。

**单个机器人对单个 frontier 的效用（先归一化，再加权）：**

```
U(i, f) = V(f) / s_V  −  λ · A(i, f) / s_A  +  Σ_k w_k · T_k(i, f, 状态)
```

- `V(f)`：frontier 周围 0.5 m 内的最大价值，和单机版相同。
- `A(i, f)`：**路径代价，单位是动作数**。在共享可通行栅格上用 A\* 从机器人 i 的位置规划到 f，代价 = 前进动作数（路径长度 / 0.25 m）+ 转向动作数（起始朝向对准路径的转角，加上路径上各拐点的转角，除以 30°）。找不到路径时退回欧氏距离，按"直线前进 + 起始转向"折算成动作数。
- `s_V`、`s_A`：**固定的典型尺度**，写在配置里，整个实验不变。不用每一步的 min–max 归一化：价值的范围很窄（冒烟测试里最好的 frontier 也只有 0.12–0.23），min–max 会把噪声放大成满量程的差异。尺度值从单机运行的统计里定（例如 frontier 价值和路径动作数的中位数），定下来之后和调参集一起固定。
- `T_k`：预留的附加项，初始权重全为 0，各自带自己的固定尺度。计划中的两项：**非重叠信息增益**和**队友轨迹复用惩罚**。附加项通过注册表接入，加一项不需要改分配器。

归一化之后 λ 是无量纲的，量级在 1 附近，表示"一个典型路径代价抵多少个典型价值"。

**联合分配：**

```
(f1*, f2*) = argmax  U(1, f1) + U(2, f2)
             约束    ‖f1 − f2‖ ≥ d_min
```

frontier 数量通常不超过二十个，直接枚举所有有序对。A\* 的次数是 2·|F|，在 1000×1000 的栅格上可以接受；如果实测太慢，先按欧氏距离筛出每台的前 K 个候选再算 A\*。

**约束无法满足时的回退**（只有一个 frontier，或所有 frontier 都挤在 d_min 以内）：效用高的那台去最好的 frontier；另一台取消间距约束，去它自己效用最高的另一个 frontier；如果只有一个 frontier，另一台原地转圈观察，不占用这个 frontier。

**迟滞：** 记上一次的分配为 A_prev。先把 A_prev 里的 frontier 匹配到当前的 F（0.5 m 内算同一个，和单机版的粘滞规则一致）。只有当新方案的总分 `J(A_new) > J(A_prev) + τ` 时才切换；A_prev 里的 frontier 消失了，就对受影响的机器人重新分配。τ 也是归一化之后的无量纲数。

**只有一台需要分配时**（另一台在初始化或正走向目标）：把另一台的当前目标当作已占用，对这一台做带间距约束的单机选择。

需要调的参数：λ、d_min、τ，在调参集上扫。

### 3.5 发现目标之后

物体地图是共享的，一台机器人检测到目标，两台都"知道"。**采用方案 a**：离目标近的那台去导航并负责 STOP，另一台继续探索。（没有采用的方案 b 是两台都走向目标。）

选 a 的理由来自单机冒烟测试：20 个 episode 里 13 个失败**全部是误报**（把别的东西当成目标然后 STOP）。两台机器人看到的画面更多，误报机会也更多，而任意一台 STOP 都会结束 episode。让第二台继续探索，至少不会让两台一起扑向同一个误报。这也意味着双机器人的成功率**不一定**比单机高，这是需要实验回答的问题，不是既定结论。

### 3.6 没有 frontier 时

单机版在没有 frontier 时直接 STOP（必然失败）。双机时改成：该机器人原地转圈等待；只有两台都没有 frontier、也没有目标时，才结束 episode。

### 3.7 指标

记号：L1、L2 分别是 R1 起点、R2 起点到目标的最短测地距离（L1 就是 episode 自带的 `geodesic_distance`，L2 在生成 R2 起点时算好并保存）。P1、P2 是两台各自实际走过的路径长度。S 是成功标志。w 表示调用 STOP 并成功的那一台。

每个 episode 记录：

| 指标 | 定义 |
|---|---|
| SR | 任意一台成功即 S = 1 |
| 团队 SPL（主指标） | `S · L / max(P1 + P2, L)`，其中 `L = min(L1, L2)` |
| 团队 SPL（L1 版） | 同上，但 `L = L1`。这是 CoRelNav 的定义（见第 7 节），同时记录以便对照 |
| 成功者 SPL | `S · L_w / max(P_w, L_w)`：只看成功那台自己的路径和它自己起点的最短距离 |
| 成功时的联合步数 | 成功的 episode 记录结束时的联合步数；失败的记为空 |

由"成功时的联合步数"可以事后算出任意预算下的成功率，例如 **SR@250**：成功且联合步数 ≤ 250 的比例。主实验只跑一次 500 联合步，不需要为 250 步再跑一遍。

辅助记录（用于分层和排查）：每台的路径长度和动作数、是哪一台调用的 STOP、STOP 时到目标的距离、失败原因、结束时每台的位置和导航目标点。

单机基线没有 R2：P2 = 0，L = L1，此时三种 SPL 都等于标准 SPL。

需要注意的一点：`min(L1, L2) ≤ L1`，所以主指标对双机方法比 L1 版更严格。和单机基线比较时，两种版本都会报告。

### 3.8 基线

全部由同一套代码通过配置切换，保证除了被比较的那一点之外其余完全相同。下表按 GPU 时间不够时的**优先级**从高到低排列。

| 优先级 | 方法 | 机器人数 | 地图 | frontier 选择 | `assigner` |
|---|---|---|---|---|---|
| 1 | 单机 VLFM | 1 | — | 原版规则 | `vlfm` |
| 2 | 两台独立 VLFM | 2 | 各自独立，互不通信 | 各自用原版规则 | `vlfm` |
| 3 | 共享 + 各自独立打分 | 2 | 共享 | 各自独立最大化 U(i, f)，即 3.4 的效用，但不做联合、没有间距约束 | `independent_utility` |
| 4 | 本方法 | 2 | 共享 | 联合分配（3.4） | `joint` |
| 5 | Greedy | 2 | 共享 | 各自取最近的、不与队友冲突的 frontier（不看价值） | `greedy` |
| 6 | 共享 + 原版规则 | 2 | 共享 | 各自用原版规则（按价值取最大） | `vlfm` |

第 3 条和第 4 条只差"联合"这一点，是最直接的对照。

配置项：`num_robots`、`map_sharing: shared | independent`、`assigner: vlfm | independent_utility | greedy | joint`、`fix_acyclic_enforcer`（默认 `false`，所有方法相同）。

**关于单机基线的数值**：冒烟测试的 20 个 episode 全部来自同一个场景，SR 35% **不作为**单机基线。单机基线以评测集（3.10，按场景分层抽取）上的结果为准。

### 3.9 R2 起始位姿的采样

对每个 episode，用固定随机种子离线采样一次：

1. 先在 [2, 10] m 上均匀抽一个目标距离 d。
2. 在导航网格上取候选点，要求同时满足：
   - 同一楼层：与 R1 起点的高度差 |Δy| ≤ 0.2 m；
   - 与 R1 起点互相可达（测地距离有限）；
   - 到 R1 起点的测地距离与 d 的偏差在容差内（先用 ±0.25 m）；
   - 到目标的测地距离 L2 ≥ 3 m。
3. 从满足条件的候选点里随机取一个；朝向在 [0, 2π) 上均匀随机。
4. 如果某个 d 下没有候选点，重新抽 d，最多重试若干次；仍然失败的 episode 单独列出来，不静默放宽条件。

保存到文件的字段：R2 的位置和朝向（Habitat 世界系）、R1–R2 测地距离、L1、L2、目标是否和 R1 起点在同一楼层（离 R1 最近的目标观察点与 R1 起点的高度差 ≤ 0.5 m，高度差本身也保存）、所用的随机种子。这些字段用于分层分析（例如按 R1–R2 距离、按 L2/L1 分组看各方法的差距）。

脚本是 `scripts/generate_robot2_starts.py`，输出 `data/multi_robot/hm3d_val_robot2_starts.json.gz`。只用 CPU；采样用的是按机器人尺寸重算后的导航网格（与评估时相同），不是场景自带的网格文件。

**实际采样结果**：2000 个 episode 里 1863 个采到了 R2 起点，137 个按上述规则采不到：

| 原因 | 数量 |
|---|---|
| R1 起点在楼梯上，起点高度落在两层楼之间，±0.2 m 的"同一楼层"范围只有几级台阶 | 107 |
| 有候选点，但都离目标不到 3 m，或抽到的距离没有匹配点 | 27 |
| 同一楼层内没有落在 2–10 m 内的候选点 | 3 |

**处理方式：这 137 个 episode 不进入评测集和调参集。** 失败列表和每个 episode 的原因保留在输出文件的 `failures` 字段里。后果：评测集里没有"从楼梯出发"的 episode，比完整 val 集略容易，所以单机基线的数值不能直接和论文的 HM3D 结果对比；各方法都在同一个评测集上跑，方法之间的比较不受影响。

已采样的 episode 里，R1–R2 测地距离在 2–4、4–6、6–8、8–10 m 四个区间的数量是 640、455、410、358。分布偏向近距离，是因为很多楼层没有 8–10 m 远的点，抽到大距离时只能重抽。

另有一个场景（XB4GS9ShBRE）的 37 个 episode，重算网格得到的 L1 比数据集自带的值长 0.45–0.58 m，其余吻合到 1e-5。Habitat 计算 SPL 时用的是仿真器当场算出的距离，所以本方案统一使用重算的 L1；两个值都保存在文件里。

**R2 的起点有很大比例比 R1 离目标更近（L2 < L1）：全部 1863 个里是 55%，评测集里是 47.5%。** 这意味着双机方法相对单机的优势，有一部分只是来自"多了一个离目标更近的起点"，而不是来自协作。所以**主要结论以"本方法对比两台独立 VLFM"为准**，而不是对比单机；单机基线只作为参照。

### 3.10 评测规模和统计比较

- 调参集和评测集**按场景分开**：随机取 5 个场景做调参，其余 15 个场景做评测（固定随机种子）。只有采到 R2 起点的 episode 才参与划分。
- 评测集：200 个 episode，15 个场景各 13 或 14 个；在每个场景内按 R1–R2 距离的四个区间轮流抽取，所以四个区间的数量是 50、50、51、49。
- 调参集：50 个 episode，5 个场景各 10 个，只用于选 λ、d_min、τ。
- 划分脚本是 `scripts/make_eval_splits.py`，结果存在 `data/multi_robot/hm3d_val_splits.json`，里面同时保存了两个集合和全部可用 episode 的分布统计（类别、距离区间、同楼层比例、L1/L2 均值）。评测集的类别分布和同楼层比例（81%）与全部可用 episode（82%）接近。
- 汇总脚本按 episode 把各方法的结果对齐，做**逐 episode 配对比较**：
  - 成功率：2×2 配对表（两个方法各自成功/失败的 episode 数）和 McNemar 检验；
  - SPL 和联合步数：逐 episode 差值的均值，加配对 bootstrap 的 95% 置信区间；
  - 同样的比较按 3.9 记录的距离分层再做一遍。
- 所有结果除了在整个评测集上报告之外，**额外报告"目标与 R1 起点在同一楼层"的子集**。

### 3.11 结果完整性：损坏标记、自动重跑、重复抽查

**背景。** 评测用的机器会偶发内存类故障，原因未确定（内存检测没有发现问题）。已观察到三种表现：

- 进程崩溃，或某个模型 server 崩溃。server 崩溃后评估进程重试 10 次就退出，**退出码是 0**。
- numpy 从布尔掩码取下标时，某个下标多出一个高位（例如轴长 640，下标却是 2^51+1131）。四次出现，多出的位都在 8 字节整数的同一个字节里。
- 理论上还可能有不报错的悄悄损坏（比如地图里某个值被改了）。目前没有观察到，但也无法排除。

第二种最危险：VLFM 在更新地图时把任何 `IndexError` 都当成"到了地图边缘"并结束 episode，这个 episode 会被悄悄记成失败。

**损坏标记。** `BaseObjectNavPolicy._pre_step` 的 `except IndexError` 里先判断下标是不是明显损坏：下标的绝对值超过数组大小的 1000 倍（`vlfm/utils/hw_corruption.py`）。

- 是：把这个 episode 标记为 `hw_corruption: true`（写进逐 episode 的 JSON），并立即结束它。不重算这一步。
- 不是：保持原样，按"到了地图边缘"处理。

双机策略里，一台机器人"没路可走"时本来会原地转圈等待；如果这一步带有损坏标记，就不转圈，直接结束 episode，标记照样写进 JSON。

**评测脚本**（`scripts/eval_multi_robot.py`）只依据逐 episode 的 JSON 文件工作，不看退出码，也不解析控制台日志：

- 一个 episode 只有在它的 JSON 存在时才算完成。进程崩溃、server 崩溃、超时留下的缺口，下一轮自动补跑。
- JSON 里 `hw_corruption` 为真的 episode，结果文件移到 `corrupted/` 目录留档，然后重跑。
- 按场景分段运行。评测中断后重新执行同一条命令，只会跑还缺的 episode。
- 每段运行前检查 4 个模型 server 是否都在监听，有缺的就全部重启。
- 每个 episode 最多尝试 3 次，仍然没有干净结果的会列出来，脚本以非零退出码结束。

**重复抽查。** 固定随机种子抽取 20% 的 episode 再跑一遍，和第一遍逐字段对比（成功与否、到目标距离、步数、是否调用 STOP、团队 SPL、各机器人的路径长度等）。正常运行是完全可复现的（阶段 0 的回归测试已经验证），所以两遍不一致就说明其中一遍被悄悄损坏了。不一致的 episode 跑第三遍来裁决：第三遍和哪一遍一致就采用哪一遍；三遍互不相同则标为未解决。

每次评测的完整性记录写在 `integrity.json` 里：因损坏标记重跑了哪些 episode、哪些运行没有留下结果、server 重启了几次、重复抽查对比了多少个、有多少个不一致以及如何裁决。报告结果时一并报告这些数字。

**局限。** 重复抽查只覆盖 20% 的 episode。如果抽查发现的不一致比例是 p，那么没被抽到的 80% 里预计也有大约同样比例的 episode 受影响，而且无法定位。所以如果抽查的不一致比例不是接近于零，就应该把重复比例提高到 100%。

**只指定部分 episode 运行**：数据集类型 `ObjectNavSubset-v1`（`vlfm/multi_robot/dataset.py`）只保留环境变量 `VLFM_EPISODE_LIST` 指向的清单里的 episode。评测划分和重跑都靠它。

### 3.12 相对原版 VLFM 的行为改动

本方案对原版 VLFM 的行为只做了下面这一处改动，其余改动要么默认关闭，要么只在异常情况下触发。

**物体点云随机抽样的种子。** 原版在两处用随机数：记录目标点云时随机抽 5000 个点，以及给"不可靠的检测"打一个随机标签。它们用的是 numpy 的全局随机数发生器，而且在 episode 之间不重置。这带来三个问题：

- 录视频时，画检测框的随机颜色也从同一个发生器取数，所以录不录视频，抽到的点不同。实测 20 个 episode 里，11 个的导航目标点差了几毫米，1 个的结果有实质差别（到目标距离 8.08 m 对 9.25 m）。事后给某个 episode 补录的视频，会和评测时的数字对不上。
- 一个 episode 的结果取决于同一进程里它前面跑过哪些 episode。重跑单个 episode 得不到原来的结果，重复抽查（3.11）也会把这种差异误报成损坏。
- 两台机器人共用一个发生器时，一台消耗随机数会改变另一台的抽样，方法之间的差异里会混进随机数序列的影响。

**改动**：每个物体地图有自己独立的发生器（`ObjectPointCloudMap._rng`），每台机器人一个。每个 episode 开始时，用（场景名和 episode 编号算出的种子，机器人编号）重置。可视化和其他代码不再影响它。抽样的算法、点数和其余逻辑都没有变，变的只是种子。

种子由任务的 `episode_seed` 传感器提供，由双机策略（单机模式也经过它）在 episode 开始时设置。不经过这条路径的原版配置（`vlfm_objectnav_hm3d`）使用固定的初始种子，行为和原版一样依赖运行历史。

后果：改动之后的逐 episode 结果，和改动之前（阶段 0 及更早）的不能逐个对比。新的参照基准是改动后重新跑的那 20 个 episode，"不录视频"和"录视频"各一次，两者应逐个完全一致。

**基准结果（2026-10-05）**：场景 5cdEh9F2hJL 的前 20 个 episode，单机模式（经双机配置，`num_robots=1`），预算 500 步。SR 35%（7/20），SPL 0.149。录视频与不录视频逐个完全一致（20/20），比较的字段包括成功与否、SPL、到目标距离、步数、失败原因、导航目标点和 `multi_robot` 统计。只有三个字段不参与比较：`debug`、`start_yaw` 和 `render_below_images`，它们只在录视频时写入，是叠加在视频上的文字，不参与决策。录视频的那次因下标损坏在 `value_map.visualize` 崩溃了两次（第 51 位、第 55 位），缺的 episode 用子集数据集单独补跑。补跑的结果也一致，说明每个 episode 的结果确实与它在进程里的先后位置无关。结果保存在 `~/yeen/results/base_novideo` 和 `~/yeen/results/base_video`，不入库。

这一处 1000×1000 的布尔下标是录视频时写下标最多的操作，也是损坏最常出现的位置，所以正式评测不录视频，需要视频的 episode 事后单独补录。

**默认关闭或只在异常时触发的改动**（列在这里备查）：

- `fix_acyclic_enforcer`：默认 `false`，保持原版行为（1.5）。
- 损坏下标的标记：只在下标明显损坏时触发（3.11）。
- 双机策略里"没路可走时原地转圈"：只在有两台机器人、且其中一台还能继续搜索时生效；单机时和原版一样直接结束（3.6）。

### 3.13 检测器接口

检测这一步（现在是 YOLOv7 / GroundingDINO + Mobile SAM）抽成一个可替换的接口：输入 RGB（和可选的仿真器语义观测），输出目标类别的检测框和掩码。两种实现：

- `vlm`（默认）：现有的检测器和分割器，行为不变。
- `gt`（预留）：用 HM3D 的语义标注和语义传感器给出真值掩码，用来把协作效果和检测误差分开。**这个模式放到阶段 5 之后实现**，现在只定接口、留配置项 `detector: vlm | gt`，选 `gt` 时直接报"未实现"。

实现 `gt` 模式时要注意：`vlfm/run.py` 目前会把 `semantic_sensor` 从配置里删掉，需要按配置保留。

## 4. 在 habitat-sim 0.2.4 里放两个机器人：三种方式

### 方式 A：一个 simulator，两个 habitat-sim agent

habitat-sim 原生支持：`Simulator.step` 接受 `{agent_id: action}` 字典，`get_sensor_observations(agent_ids=[0, 1])` 一次返回两台的观测。

- 优点：语义最正；两台同时步进；只加载一份场景，多出来的显存只是第二套传感器的帧缓冲（很小）。
- 缺点：改动集中在 habitat-lab 这一层，而且很多。habitat-lab 0.2.4 的 ObjectNav 任务是按单 agent 写的：动作（`MoveForwardAction` 等）只对默认 agent 调用 `sim.step`；`gps`、`compass`、`distance_to_goal`、`success`、`spl` 全部调用不带参数的 `get_agent_state()`，也就是只看 agent 0；配置里加第二个 agent 后，传感器的键名会带上 agent 前缀，下游（批处理、obs transform、可视化）都要跟着改。相当于要重写一套任务、传感器和指标。
- 两台机器人**仍然互相看不见**：habitat-sim 的 agent 没有可渲染的身体，除非另外往场景里加机器人模型并每步同步位姿。

### 方式 B：两个 simulator 加载同一个场景

每台机器人一个 Habitat 环境（两个进程，或同一进程里两个 simulator）。

- 优点：每个环境都是原样的单机 ObjectNav，habitat-lab 完全不用改。
- 缺点：
  - **显存不够**。实测这张 11 GB 的卡上，4 个模型 server 占约 9 GB，每个 Habitat 渲染进程再占约 1 GB；两个进程同时跑时峰值 11155 / 11264 MiB，Mobile SAM 出现了 17 次显存不足。这条路在这台机器上不可行。
  - 第二个环境的 episode 起点不同，它的 `gps`/`compass` 会落在自己的 episodic 系里，需要额外的坐标变换才能并到 W。
  - 两个环境的 episode 要手工保持同步，指标要跨环境合并。
  - 同样互相看不见。

### 方式 C：一个 simulator，一个 agent，位姿轮换（建议）

仿真器里仍然只有一个 agent。任务层保存两台机器人的位姿；每个环境步只服务一台机器人：把 agent 放到这台机器人的位姿上，执行它的动作（走的是 habitat-sim 原本的运动和碰撞逻辑），把新位姿存回去；然后把 agent 移到下一台机器人的位姿上，渲染出它的观测并返回。一个联合步 = 两个环境步。

- 优点：
  - **显存零增加**，只有一个渲染器、一套传感器。
  - `gps`、`compass` 读的是 agent 当前位姿、相对的是 episode 起点，所以两台的观测自动落在同一个 W 里。
  - 环境的动作空间和观测键名不变，`VectorEnv`、批处理、obs transform、trainer 主循环基本不用动。只需多加一个观测 `active_robot_id`。
  - `num_robots = 1` 时退化成原版，可以做回归测试。
- 缺点：
  - 两台机器人是轮流走而不是同时走。因为它们之间没有物理交互，结果和同时走等价，只是实现上串行。
  - 互相看不见、不会相撞。方式 A、B 同样如此。可以加一个简单的距离检查来统计"本该相撞"的次数，作为这一简化的影响评估。
  - Habitat 自带的 `distance_to_goal`、`success`、`spl` 会被位姿切换搞乱（它们会把切换当成机器人瞬移走过的路程），需要自己写一组指标来替代。方式 A 也需要重写这些指标。
  - 每个联合步要调用两遍模型 server，单个联合步的耗时大约是单机一步的 2 倍（按冒烟测试估算，未实测）。这是双机器人固有的开销，三种方式都一样。

### 推荐：方式 C

决定性的因素是显存（排除 B）和改动量（A 要重写 habitat-lab 的任务层，C 只需加一个任务子类和一组指标）。三种方式下机器人都互相不可见，A 在这一点上没有优势。以后如果需要真正的同时步进或可见的机器人身体，C 的任务类和指标可以原样迁移到 A，换掉的只是"轮换位姿"那一段。

### 5.3 分阶段计划

每个阶段结束都有一个可检查的结果，通过后再进下一阶段。

**阶段 0：基础设施，不改变行为**
- `AcyclicEnforcer.history` 改为实例属性，加 `fix_acyclic_enforcer` 开关（默认关）；逐 episode 的 JSON 日志补上导航目标点和步数（沿用已有的 `ZSOS_LOG_DIR` 机制）。
- 验收：重跑之前那 20 个 episode，逐个对比结果，目标是完全一致。

**阶段 1：R2 起点**
- 按 3.9 写采样脚本，生成并保存全部 2000 个 episode 的 R2 起始位姿和相关距离。
- 验收：在俯视图上画出若干 episode 的 R1、R2 起点，人工检查在同一楼层、可通行、互相可达。

**阶段 2：位姿轮换任务 + 指标 + "两台独立 VLFM"基线**
- 实现方式 C 的任务类和新指标；策略里放两套完全独立的单机 VLFM 状态。
- 验收：
  - `num_robots = 1` 的结果和阶段 0 一致。
  - 坐标一致性测试：两台机器人分别把深度投到 W 里，和真值俯视图对比，重叠区域的障碍物位置偏差在 1–2 个像素内。
  - 跑通若干 episode，视频里两台的画面和轨迹正确。

**阶段 3：共享地图**
- 改 `ObstacleMap`、轨迹显示；策略支持 `map_sharing: shared`。得到"共享地图、无联合分配"基线。
- 验收：视频里两台的已探索区域合并成一张图，队友的区域不会被删掉；价值地图同时包含两台的观测。

**阶段 4：协调器**
- 实现 `independent_utility`、`greedy`、`joint` 三种分配器，迟滞，A\* 动作数路径代价（带欧氏回退），固定尺度归一化；附加项接口留好，权重为 0。
- 从单机运行的日志里统计 frontier 价值和路径动作数的分布，定下 `s_V`、`s_A`，写进配置。
- 把检测抽成接口（3.13），`gt` 模式只留占位。
- 验收：单元测试覆盖间距约束、三种回退情况、迟滞不抖动；视频里两台机器人去不同的 frontier，目标不会每步来回切换。

**阶段 5：调参和评估**
- 在调参集上扫 λ、d_min、τ；在评测集上按 3.8 的优先级顺序跑各方法，时间不够时从后往前砍。
- 调参集和评估集必须不相交。两者都从 val 里按场景分层抽取，固定下来存成文件。
- 评测集 200 个 episode（见 3.10）。耗时估算（未实测，按单机 65 秒/episode、双机约 2 倍估）：单机约 3.6 小时，五种双机方法各约 7 小时，全部跑完合计约 39 小时，全程占用整张 GPU。
- 写汇总脚本 `scripts/summarize_multi_robot.py`，实现 3.10 的配对比较。

**阶段 6：消融项和真值检测**
- 实现"非重叠信息增益"和"队友轨迹复用惩罚"，各自作为一个附加项，单独开关。
- 实现检测器的 `gt` 模式，重跑主要方法，把协作效果和检测误差分开。

## 7. 与 CoRelNav 的核对（III-D、IV-A）

论文 PDF 在 `docs/` 下。下面只列和本方案有关的内容，以及两者不一致的地方。

### 7.1 任务本身不同

CoRelNav 的每个 episode 有**两个目标**（两个物体，或物体加带空间关系的语言描述），两个子任务都完成才算成功。本方案是两台机器人找**同一个**目标，任意一台到达即成功。所以它的指标和基线只能借鉴形式，数值不可比。

### 7.2 实验设置（IV-A.1、IV-A.2）

| 项目 | CoRelNav | 本方案 | 说明 |
|---|---|---|---|
| 数据 | HM3D，episode 构造沿用 VLN-Game | HM3D ObjectNav v1 val | — |
| 初始位姿 | 每个 episode 指定两台的初始位姿，所有方法共用 | 相同 | 一致 |
| 步数预算 | **600** 联合规划步 | 500 联合步 | **不一致**。500 是为了和单机 ObjectNav 的 500 步对齐 |
| 底层动作 | 前进 0.25 m、转 30° | 相同 | 一致 |
| 观测 | 480×640 RGB-D 和位姿 | 相同 | 一致 |
| 地图分辨率 | 0.075 m | 0.05 m（VLFM 原值） | 不同，无需对齐 |
| 检测与分割 | **用仿真器提供的真值实例掩码和 ID**，不用 GroundingDINO 和 MobileSAM | 用真实检测器（YOLOv7 / GroundingDINO + MobileSAM） | **重要差异**，见 7.5 |
| 分层 | 两个目标的成功区域测地距离 < 5 m 为 same-region，否则 cross-region | 按 R1–R2 距离、L1、L2 分层 | 思路相同，分层变量不同（本方案只有一个目标） |

### 7.3 指标（IV-A.3）

- SR：两个子任务都完成才成功。本方案是任意一台到达即成功。
- SPL：`S · L / max(L, P)`。**L 是从"规范的第一台机器人起点"出发、访问两个目标的最短路线**；P 对单机方法是单机路径，对双机方法是两台路径之和。
  - P 的定义和本方案一致。
  - **L 的定义对应本方案的"L1 版"**，不是 min(L1, L2)。也就是说，你这次指定的主指标（L = min(L1, L2)）和论文不同，比论文的定义更严格；和论文一致的是同时记录的 L1 版。
- 论文**没有**"完成步数"这个指标，也没有"成功者 SPL"。这两项是本方案自己加的。
- 论文另外报告了每个 episode 的语言模型 token 数，本方案用不到。

### 7.4 基线（IV-A.4）

| CoRelNav 的基线 | 定义 | 本方案里的对应 |
|---|---|---|
| Greedy（Visser 等） | 每台取最近的、不冲突的 frontier | 与本方案的 Greedy 一致 |
| Cost–Utility | 每台**独立**最大化"归一化的未知空间增益 − 加权归一化路径代价"；与论文方法用同一张地图 | 最接近"共享地图、无联合分配"，但**效用不同**：它用未知空间增益，本方案这一条基线用 VLFM 的价值地图 |
| Co-NavGPT | 用 VLM 在共享俯视图上联合分配 frontier | 本方案没有 |
| VLN-Game (Dual) | 两个独立 agent 并行，不共享信息、不协调 | 对应"两台独立 VLFM" |
| Embedding | 论文方法关掉关系验证 | 不适用 |

出入：

- 论文的表里**没有单机基线**。本方案有。
- 论文没有名为"共享地图但不做联合分配"的基线；Cost–Utility 起到类似作用，但它同时换了效用函数。已决定增加一条"共享 + 各自独立打分"基线（3.8 第 3 条），它和本方法只差"联合"这一点。

### 7.5 联合分配（III-D）

论文的做法分两层：

1. **每台机器人的候选打分**（式 3）：`P_i(f) = w_u·Ḡ_i(f) + max_τ E_i(f) − w_a·Ā_i(f) − w_h·R̄_i(f)`。
   - G：沿路径和在终点处预计新看到的未知面积（信息增益）。
   - E：任务相关的语义证据。
   - **A：可行 A\* 路径上的"前进和转向动作数"**，不是米。
   - R：路径与**队友探索历史**重合的比例。
   - 带横线的量都按固定的典型尺度做了归一化。每台保留前 K 个候选。
2. **团队联合打分**（式 4）：在候选组合里最大化 `Q = w_u·Ḡ∪ + w_o·⟨O⟩ + w_b·⟨B⟩ + w_s·⟨d_geo⟩ − w_a·Ā_Σ − w_h·⟨R⟩ − w_c·⟨C⟩`。
   - G∪：两台**不重叠**的联合信息增益。
   - ⟨d_geo⟩：两台目标之间的测地距离，作为**加分项**。
   - ⟨C⟩：成对的走廊冲突，作为惩罚项。
   - 候选组合还要先过一道硬筛选：有效、不重复、导航上可区分、间隔足够。
3. **迟滞**：候选数相同时，除非 `ΔQ ≥ Δ_h = 2`，否则保留上一次的分配。

和本方案 3.4 的对比：

| 项 | CoRelNav | 本方案（第一版） | 处理 |
|---|---|---|---|
| 语义项 | 任务条件的空间语义场 | VLFM 价值地图 V(f) | 角色相同 |
| 路径代价 | A\* 路径上的动作数（含转向） | A\* 动作数（含转向） | 已采纳：改用 A\* 动作数，欧氏距离只作回退（3.4） |
| 归一化 | 各项按固定典型尺度归一化后再加权 | 固定典型尺度归一化 | 已采纳：固定典型尺度归一化（3.4） |
| 目标间距 | 硬筛选 + 测地距离加分项 | 只有硬约束（欧氏 d_min） | 本方案更简单。加分项可以作为一个附加项接入预留接口 |
| 非重叠信息增益 | 主项 G∪ | 预留的消融项 | 与你要求的预留项一致 |
| 队友轨迹复用 | 惩罚项 R | 预留的消融项 | 与你要求的预留项一致 |
| 走廊冲突 | 惩罚项 C | 没有 | 方式 C 下两台互相不可见也不相撞，这一项在仿真里没有作用，不建议加 |
| 迟滞 | 总分差达到阈值才切换 | 相同形式（τ） | 一致。论文的阈值 2 是它那套归一化尺度下的数，不能直接搬 |

### 7.6 一个影响结论解读的差异

CoRelNav 在仿真里用真值实例掩码代替检测器，目的是"把探索和推理隔离出来"。本方案用真实检测器，而单机冒烟测试的 13 个失败全部被归为 false_positive（抽查 6 个：其中既有真正的误检，也有检测对了但数据集没把该物体列为目标的情况）。

这意味着：本方案里各方法的成功率差距，很可能被检测误报淹没，协调策略的好坏主要体现在 SPL 和步数上，而不是 SR 上。如果之后想单独评估协调策略，可以加一组"真值检测"的对照实验（用仿真器的语义传感器代替检测器）。已列入阶段 6（检测器的 `gt` 模式，见 3.13）。
