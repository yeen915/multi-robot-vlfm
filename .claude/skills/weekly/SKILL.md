# 周报

读者是导师：熟悉机器人导航和 VLFM，但没看过这个仓库的代码。写结论和数字，不写实现细节和文件名。

## 1. 收集材料（默认最近 7 天，用户可以指定起止日期）

```bash
git log --since="7 days ago" --date=short --pretty="%ad %s" multi-robot
ls -lt outputs/eval/ | head -30            # 本周修改过的运行
cat outputs/eval/*_summary.txt 2>/dev/null # 对比表
```

- `docs/multi_robot_design.md` 第 5 节的阶段清单：本周完成的项（看日期）、当前阶段还没做的项。
- 本周的实验：每个运行的 `integrity.json`、汇总表、设计文档里记下的结论。只用已经完成并通过完整性检查的结果。还在跑的写成"进行中"，不写数字。
- 本周遇到的问题：硬件故障、需要改设计的发现（例如尺度问题）、失败的尝试。

## 2. 格式（一页以内，约 500–800 字）

```markdown
# 周报（YYYY-MM-DD – YYYY-MM-DD）

**本周小结**：两三句话：做到了哪个阶段，最重要的一个结果。

## 进展
- 3–5 条，每条一句话，写做成了什么（不是做了什么操作）。

## 实验结果
- 最多一张小表（3–6 行）：方法、episode 数、主要指标。
- 一两句话说明结论和依据：差别多大、是否显著、样本量。

## 问题与应对
- 1–3 条：问题、影响、怎么处理的或打算怎么处理。

## 下周计划
- 2–4 条，对应阶段清单里的下一步。

## 需要讨论（可选）
- 需要导师决定或给意见的事，没有就省略。
```

## 3. 写作要求

- 指标第一次出现时用括号简短说明，例如"SPL（按路径长度加权的成功率）"。
- 数字要有出处：只写实验里实际测到的值，并写出样本量。不显著的差别写成"没有明显差别"，不要写成"略好"。
- 不写服务器账号、路径、密钥、Tailscale 等运维细节；硬件故障只写对进度的影响和应对。
- 不夸大：没跑完的实验、临时的参数值要标明。

## 4. 输出

1. 保存为 `docs/weekly/YYYY-MM-DD.md`（结束日期），本地提交（不推送）。
2. 在回复里贴出全文，方便用户直接复制发送。
3. 问用户要不要调整语气或长度。
